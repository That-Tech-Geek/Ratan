# Production Specification: Browser Cache + Offline Data Plane\n\n## Objective\nMake Gyaan Saathi resilient to intermittent 2G/3G and browser restarts without treating browser storage as authoritative application storage.\n\n## Storage boundaries\n\n| Layer | Technology | Purpose | Authoritative? | TTL / retention |\n|---|---|---|---|---|\n| HTTP asset cache | Browser Cache Storage via service worker | App shell, immutable Next static assets, public diagnostic payloads | No | Versioned; old versions deleted on activation |\n| Public content cache | Cache Storage (gyaan-saathi-data-*) | Diagnostic question payloads | No | 24h client freshness target |\n| Durable write queue | IndexedDB via Dexie | Student responses waiting for acknowledgement | No, but durable locally | Until server acknowledgement |\n| Server database | PostgreSQL | Sessions, responses, audit trail | Yes | Per retention policy |\n| Service worker | Cache Storage + Background Sync | Rehydration and sync signalling | No | Versioned |\n\nNever put authentication tokens, private student records, or personalized server responses into a shared Cache Storage cache.\n\n## Read path\n1. UI requests public diagnostic content.\n2. Service worker uses network-first for /api/v1/diagnostic/questions.\n3. Successful public responses are stored in a versioned Cache Storage namespace.\n4. If the network fails, the cached response is returned.\n5. UI may additionally use the app-level Cache Storage helper when the service worker is unavailable.\n6. A cache miss while offline is an explicit empty-state, not fabricated data.\n\n## Write path\n1. Every student response is written to IndexedDB before network transmission.\n2. Each queue item receives a UUID idempotency key.\n3. Online clients attempt batches of at most 20 items.\n4. Items move pending -> syncing -> acknowledged (delete after acknowledgement) or back to pending after transport failure.\n5. Server acknowledgement is the only condition that removes an item.\n6. Browser/service-worker lifecycle events trigger another sync attempt.\n7. Retries must use exponential backoff with jitter once the queue moves beyond the current MVP.\n\n## Production API contract\nPOST /api/v1/sync/batch\n\nRequest: items[], id (UUID idempotency key), entity, action, payload, createdAt, client/session identifier.\nResponse: acceptedIds[], duplicateIds[], rejected[] with stable machine-readable reason, server timestamp.\n\nThe endpoint must validate the entire request against a schema, authenticate the actor, enforce tenant/school authorization, and perform idempotent upserts in a database transaction.\n\n## Required server-side data flow\nThe current repository's sync endpoint records audit entries. Production must additionally materialize accepted diagnostic_response and likert_response events into their normalized tables and associate them with an authenticated student/session. The browser queue must therefore carry a server-recognized session identifier rather than only a question identifier.\n\n## Cache invalidation\n- Cache names are versioned.\n- Service-worker activation removes previous application cache generations.\n- Public question payloads use a content version from the API.\n- A future content manifest should permit explicit invalidation without waiting for TTL.\n- No Cache-Control header from an upstream personalized response should be overridden into a public cache.\n\n## Quota and eviction\nCache Storage and IndexedDB are browser-managed storage and can be evicted. Therefore:\n- keep the shell small;\n- cap runtime cache entries;\n- keep diagnostic payloads compact;\n- expose queue size and sync status;\n- never claim that local storage is permanent;\n- request persistent storage (navigator.storage.persist()) where supported after user interaction;\n- monitor navigator.storage.estimate() and surface low-storage conditions.\n\n## Security\nProduction deployment requires HTTPS, authenticated sessions, authorization scoped to school/tenant, CSRF protection where cookie authentication is used, strict request-body/schema validation, rate limits on sync, payload size limits, no sensitive data in URLs, no sensitive data in Cache Storage, audit records that cannot be forged by arbitrary clients, encrypted transport and encrypted managed database storage, and defined deletion/export/retention workflows.\n\n## Reliability targets\n- Cold online load: app shell usable after first successful load.\n- Warm offline load: shell renders without network.\n- Cached diagnostic: available offline after it has been successfully fetched once.\n- Response durability: browser refresh/restart does not lose queued responses.\n- Sync correctness: accepted response is never duplicated server-side.\n- Sync failure: transport failure never deletes local data.\n- Version upgrade: new service worker does not retain obsolete cache generations.\n- Storage pressure: bounded caches and observable queue state.\n\n## Test matrix\nAutomate at minimum: first install online; reload offline; question fetch online then offline reload; answer while offline; browser restart with pending queue; reconnect and batch acknowledgement; duplicate batch submission; partial batch rejection; failed request followed by retry; service-worker version upgrade; cache eviction / unavailable Cache Storage; unsupported Background Sync; low-storage condition; malformed sync payload; unauthorized sync request.\n\n## Definition of production-ready\nThe system is production-ready only when the browser data plane is treated as an unreliable edge cache and queue, while the server provides authenticated, idempotent, transactional persistence. The current implementation establishes the client-side Cache Storage + IndexedDB foundation; the remaining production gate is the authenticated server-side session/idempotency contract and its migration/test coverage.
